# Submit PR or MR

## 触发门禁

这个 Skill 只能由用户明确调用。只有用户消息中明确出现 `$submit-pr-mr`，或明确要求“使用 submit-pr-mr”/“Use submit-pr-mr”，才可以继续；仅仅提到 PR、MR、提交、推送、审查或这个名称都不算调用。

通过门禁后，先报告“已显式触发 `$submit-pr-mr`；开始检查当前工作区。”再读取项目、执行命令或写入文件。未通过门禁时立即停止，不读取项目内容，不创建状态文件，不做任何本地或远程写操作。

显式调用授权本流程完成分支创建、提交、推送和创建 PR/MR，但不授权合并、部署、发布、强制推送、删除分支、修改生产数据或吸收与目标 diff 无关的改动。

## 规则优先级与默认值

按以下顺序确定每个动作：用户最新明确要求、仓库 `AGENTS.md` 和贡献指南、PR/MR 模板与项目配置、当前 Git 远程和平台约定、以下默认值。项目要求不明确时继续使用默认值，并在最终报告列出采用的假设；未知项目约定本身不是阻塞条件。

默认值如下：

- base/target 使用远程默认分支；无法读取时使用当前项目明确标出的主分支，否则使用当前分支的上游基线。
- 分支使用 `guang/<短主题>`；主题只包含小写字母、数字和连字符，并检查本地及远程冲突。
- 提交信息使用项目已有格式；没有格式时使用简短、祈使语气的 Conventional Commit 风格主题。
- PR/MR 标题沿用提交主题；描述包含目的、主要改动、实际验证、未验证边界和风险。
- GitHub 使用项目指定工具或已认证的 `gh`，GitLab 使用项目指定工具或已认证的 `glab`；其他平台遵循项目提供的命令或接口。
- 没有可识别的验证入口时，始终运行 `git diff --check`，并按已识别的项目类型选择有界默认：`go.mod` 使用 `go test ./...`，`Cargo.toml` 使用 `cargo test --all-targets`，存在测试目录且 `pytest` 可用的 Python 项目使用 `python -m pytest`，存在 `package.json` 测试脚本的 JavaScript/TypeScript 项目使用其锁文件对应的包管理器运行该脚本。没有匹配的项目类型或自动化入口时，报告“未发现可运行的自动化套件”，不声称测试覆盖完整，也不临时猜测新的命令。

## 工作范围和安全边界

- 固定 Git 根目录、当前 `HEAD`、当前分支、默认远程，以及调用开始时的 staged、unstaged、untracked 和相对默认基线的分支差异。把调用开始时能归属于本次目标的 code diff 作为范围。
- 先读取仓库规则和与验证、分支、提交、PR/MR 有关的说明。发现明显无关、无法归属或敏感路径时停止并报告，不替开发人员猜测提交范围。
- 保留已有用户改动，不执行 reset、clean、覆盖式 checkout、rebase、force push 或删除分支。修复只能触及目标 diff 和解决已证实问题所需的直接依赖。
- 不打印密钥、令牌、Cookie、私钥、DSN、完整远程凭据或真实账户标识。敏感内容出现在 diff、日志或命令输出中时，报告路径和解除条件即可。
- 不访问生产，不执行不可逆迁移，不修改远程保护规则，不为了通过检查临时降低测试范围或修改产品配置。

## 1. 检查并验证项目

1. 记录初始快照：仓库根目录、分支、`HEAD`、默认基线、远程名称和 URL 的非敏感摘要、完整 changed paths，以及目标 diff 的 staged/unstaged/untracked 组成。分别检查 staged、unstaged 和 untracked 内容，并运行 `git diff --check`。既没有未提交目标改动，也没有基线到当前 `HEAD` 的目标分支差异时停止并报告。
2. 扫描项目当前的验证入口和交付规则。优先查看 `AGENTS.md`、`CONTRIBUTING`、PR/MR 模板、`Makefile`、`package.json`、`pyproject.toml`、`tox`/`nox`、`Cargo.toml`、`go.mod`、`.github/workflows`、`.gitlab-ci.yml` 以及项目已有的 verify/check 脚本。只读取与当前项目和目标 diff 相关的文件。
3. 建立一次去重后的验证计划：
   - 有本地 `verify` 或 CI job 的，运行其声明的本地等价命令；
   - 有自动化测试套件的，运行项目规定的全量套件；
   - 聚合命令已经包含的 lint、类型检查或测试只运行一次；
   - 项目规范不完整时，使用本 Skill 的默认验证入口并在报告中标注假设；
   - 只有托管 CI 能运行的检查，不把查看 workflow 文件当成已运行；如果该检查是项目要求的合并门禁且无法在当前环境验证，报告验证阻塞并停止交付；
   - 不自动 dispatch 远程 workflow，不访问生产，不伪造 CI 或外部审查结果。
4. 按计划运行验证，记录实际命令、退出状态、关键失败位置和环境限制。验证失败先判断是代码问题还是缺失依赖、端口、凭据、服务、账户限制等环境问题；无法可靠区分时按复杂或阻塞问题停止。
5. 验证期间保持 `HEAD`、目标路径和用户授权不变。若代码、基线或 diff 被其他操作改变，丢弃旧结论，重新采集快照。

## 2. 按检查结果处理

每次检查完成后，只选择以下三种结果之一：

| 结果 | 处理 |
| --- | --- |
| 简单问题 | 触发场景明确，根因可由代码或命令事实确认，修复范围小，且不改变未确认的产品、API、schema、权限、安全或数据语义。直接修复，记录路径和原因，然后从第 1 步重新执行完整检查。 |
| 复杂或阻塞问题 | 解决方案不清晰、范围较大、需要产品/权限/schema/安全决策，重复失败没有收敛，验证被必需环境或授权阻塞，或无法证明改动属于当前 diff。立即停止，不创建分支、不提交、不推送、不创建 PR/MR；报告证据、影响、已完成验证和需要开发人员决定的唯一问题。 |
| 没有问题 | 所有适用的本地检查通过，必要的合并门禁已有可核验结果，`git diff --check` 通过，目标 diff 已复核且没有待处理 finding。进入第 3 步。 |

简单修复后必须重新运行同一套去重验证；不能只运行受影响的单个测试就宣布干净。相同失败连续出现、修复扩大范围或新问题需要不同方案时，改判为复杂或阻塞并停止。

## 3. 创建分支、提交、推送和 PR/MR

只有第 2 步得到“没有问题”才能继续。

1. 冻结最终 diff 和验证证据，重新检查 `HEAD`、基线、changed paths、敏感路径、暂存范围和 `git diff --check`。若快照变化，回到第 1 步。
2. 按项目规则确定 source 分支；没有规则时使用 `guang/<短主题>`。若目标范围只有基线到当前 `HEAD` 的已提交差异，且没有 staged、unstaged 或 untracked 的目标改动，则复用当前非默认 source 分支；若当前分支是默认或受保护分支，则从当前 `HEAD` 创建新的 source 分支。这个 branch-only 路径不暂存文件，也不创建空提交。若存在未提交目标改动，则从当前 `HEAD` 创建新工作分支并保留这些改动；检查本地和远程分支冲突，必要时使用短后缀。
3. 只有存在未提交目标改动时，才暂存目标范围和本流程产生的直接修复。不能用 `git add -A` 把无法归属的文件带入提交。提交前再次查看 staged diff、文件列表和敏感路径。
4. 只有存在未提交目标改动时，才按项目提交规范生成 commit message 并创建普通提交；没有规范时使用默认格式。branch-only 路径保留已有提交并跳过提交步骤。按项目 PR/MR 模板生成标题和正文；没有模板时使用默认结构，并在报告中标明假设。
5. 用项目指定的远程工具推送 source 分支并设置 upstream。禁止 amend 他人提交、force push 或删除远程分支。推送认证失败时保留本地分支和提交，报告准确阻塞原因。
6. 根据项目要求和远程主机创建 PR/MR：
   - GitHub 使用项目指定工具或已认证的 `gh`；
   - GitLab 使用项目指定工具或已认证的 `glab`；
   - 其他平台使用项目明确提供的 CLI/API；
   - 项目没有平台要求时，根据远程主机选择上述默认工具。
7. 创建时明确传入项目要求的 base/target、head/source、标题、描述、模板字段和标签字段。缺少某个可选字段时使用默认值并报告；必填信息无法确定时使用合理默认值继续，并在报告中列出假设。
8. 记录 PR/MR URL、编号、base/target、source/head、提交 SHA 和平台状态。创建成功后不要自动合并、关闭、打标签、部署或修改远程设置。

## 4. 审查新建的 PR/MR

创建成功后立即进行只读审查，并报告结果。

1. 检查当前上下文中可用的审查 Skill。只有存在明确适用于该平台 PR/MR、且能覆盖本次审查目标的 Skill 时才调用它；传入新建 URL、完整 diff、验证证据和“只读审查、发现问题后报告”的边界。审查 Skill 的调用是可选能力调用，不是对其他 Skill 的运行时导入。
2. 没有合适的审查 Skill 时，使用平台 CLI 或 API 做只读检查：读取 PR/MR 元数据和变更，查看现有 review、评论、required checks、CI 状态、合并冲突和审批状态。处理 review threads 的工具只有在确实存在待处理线程时才适用，不能代替初始审查。
3. 将结果分为：未发现当前可见问题、发现需要开发人员处理的问题、外部审查或检查仍待完成、审查被权限或平台阻塞。对每项 finding 给出文件/位置、影响、证据和建议下一步；不要在第 4 步自动修改、追加提交或重新推送。

## 5. 结束报告

结束时报告：

- 触发确认和工作流是否完成；
- 初始与最终分支、提交 SHA、目标 changed paths；
- 实际运行的验证命令、结果、修复轮次和采用的默认假设；
- 未验证边界、环境限制和阻塞项；
- 若停止，属于简单修复、复杂问题还是阻塞，以及证据、影响和需要的决策；
- 若创建成功，PR/MR 平台、URL、编号、base/target、source/head 和创建状态；
- 第 4 步使用的审查 Skill 或平台只读检查、可见 finding、待完成的外部检查和权限限制。

只有在所有适用验证通过、目标 diff 已复核、PR/MR 已成功创建并完成第 4 步只读审查后，才能报告本 Skill 工作结束。审查仍待外部完成时，明确写“已创建，外部审查或检查待完成”，不要把它描述为已批准或可合并。
